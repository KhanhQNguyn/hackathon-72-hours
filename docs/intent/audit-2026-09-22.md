## 1.3 OpenAI integration robustness

**Status: Confirmed broken in several ways (all fixed in Phase 2); real
model behaviour Cannot verify without API key.**

`openai_service.dart` (before Phase 2):
- **Markdown fences / prose.** `_completeJson` did a bare `jsonDecode(content)`.
  With `response_format: json_object` the API normally returns bare JSON, but
  a fenced block or leading prose from any model/endpoint change would raise
  and be reported as "unexpected reply shape" — no recovery. Broken →
  fix: strip fences, extract the first balanced JSON object.
- **Key tolerance.** Exact-key lookup only (`json['intentType']`). A
  differently-cased or snake_cased key silently reads as `null`
  (→ `unrecognized` / empty listing). Broken → fix: case- and
  separator-insensitive lookup.
- **Type safety.** Post-processing casts (`json['targetDescription'] as String?`,
  `JobListing.fromJson`'s `as String?`, `reasoning as String?`) run *outside*
  the try/catch that converts errors to `OpenAiException`. A model returning
  a number or list there throws a `TypeError`, which no call site catches
  (they catch `OpenAiException` only) → the flow falls into `start()`'s
  catch-all and ends in `ErrorState` instead of degrading. Broken → fix:
  tolerant getters, and every failure surfaces as `OpenAiException`.
- **Transport errors.** `_client.post` errors other than `TimeoutException`
  (`SocketException`, `http.ClientException`, TLS) propagated raw — same
  "not an `OpenAiException`" problem, and this is the *no network / captive
  wifi at the demo venue* case. Broken → fix.
- **Retry/backoff.** 429 and 5xx: retried twice with linear 1s/2s backoff
  (**Confirmed working**); `Retry-After` was ignored; **timeout was not
  retried at all** (threw immediately). Fix: honour `Retry-After` (capped),
  retry a timeout once.

Call sites (before Phase 2): `_parseIntent`, `_narrateListing`,
`_describeImages`, `_structurePdf`, `_resolveField` catch `OpenAiException`
and fall back to non-AI behaviour — **Confirmed working** for that
exception type. Gap: `submitApplication()` called `ai.matchElement` with no
catch, so an AI outage turned a clearly-best submit candidate into a
failure. Fixed.

Prompt files (`lib/services/prompts/*`): reviewed for fragility — they ask
for a fixed JSON shape, name concrete noise to ignore (listing), and require
`confidence` < 0.7 for ambiguity (matching). Whether the real model obeys
them is **Cannot verify without API key**; the unit tests only prove
parsing/guards against a scripted client.

## 1.4 The two file flows

### (a) Settings CV picker → profile DB

**Status: Confirmed working on Android by trace; Cannot verify without
device end-to-end.**

Trace: `settings_screen.dart` `_pickCv()` → `FilePickerService.pickCvFile()`
→ `setState(_cvFilePath)` → user presses **Save** → `_save()` builds the map
→ `ApplicantProfileService.saveProfile()` → `sqflite` insert + secure-storage
writes. Findings:
- On desktop the failure is the missing `sqflite` Windows plugin (1.1).
  `_save` catches it and shows the "could not save" snackbar, and
  `_load`'s `getProfile` failure is only `Logger.log`ged — the form silently
  shows empty fields. On Android neither should trigger, but the silent
  `_load` catch could still mask a real bug (a corrupt DB) as "no profile
  yet". Fixed: `_load` failure now tells the user.
- **UX gap that also explains bug 5:** picking a file only fills the on-screen
  path; nothing is saved until **Save profile**, and nothing said so. Fixed:
  the pick is announced with an explicit "press Save profile".
- **Android detail — Cannot verify without device:** the saved path is
  whatever `file_picker` returns; on Android that is normally a copy in the
  app's cache directory, which the OS may clear. Since the live form flow no
  longer uses this path (below), the impact is limited to the profile screen
  showing a stale path.

### (b) Live form-fill file upload

**Status: Confirmed broken (design), fixed. Definitive plugin answer below.**

**Definitive answer.** Checked `flutter_inappwebview` **6.1.5** with
`flutter_inappwebview_android` **1.1.3** (`pubspec.lock`). The Android side
implements `WebChromeClient.onShowFileChooser` natively:
`flutter_inappwebview_android-1.1.3/android/src/main/java/com/pichillilorenzo/flutter_inappwebview_android/webview/in_app_webview/InAppWebViewChromeClient.java:836`
→ `startPickerIntent(...)`, with the result returned through
`onActivityResult` (`:842+`). `grep -rn "FileChooser"` over the Dart code of
`flutter_inappwebview_android` and `flutter_inappwebview_platform_interface`
finds **no Dart-level callback** — no `onShowFileChooser` /
`androidOnShowFileChooser` exists in this version. So: **the chooser is fully
automatic; there is nothing to configure or wire**, and milestone 21's
"wire `onShowFileChooser`" instruction cannot be followed as written — the
earlier code comment was right and the milestone spec is wrong. Whether it
actually opens on a device is **Cannot verify without device**.

What *was* broken is our use of it (`_attachCv`, before Phase 2):
1. It called our own `FilePickerService.pickCvFile()` **and then**
   `triggerFileChooser()` — two native pickers back to back, and the path
   from ours is never given to the page (browsers cannot set file inputs).
2. Nothing was said before the page's chooser opened — a blind user lands in
   an unannounced system file picker.
3. It then announced "CV file selected: X" without checking anything was
   attached.

**Open risk — Cannot verify without device, and likely to bite:** the chooser
is opened by JS `input.click()` run through `evaluateJavascript`. Chromium
(and so the Android WebView) generally requires *transient user activation*
to open a file picker; a scripted click with no real tap behind it may be
ignored. If so `triggerFileChooser` still returns `success: true` (the
`click()` ran), no chooser opens, `awaitFileChooser` gives up after 5 s (no
app pause seen) and `getFileInputName` returns nothing — the flow then says
"No CV file was attached, skipping it", i.e. it fails **safe and spoken**, not
silently. A working fallback would be to focus the input and ask the user to
activate it themselves with TalkBack (a real gesture); not built, because it
needs a device to design against.

Fixed: announce first ("your phone's file picker will open; choose your CV
again, then say done"), open only the page's chooser, wait for "done", then
read the input's file name via JS to confirm before narrating success — else
narrate that nothing was attached and skip. The saved profile CV path is not
auto-attached: browser file inputs cannot be set programmatically (already
documented in `02-spec.md` §1), so the user always re-picks at that moment.

## 1.6 Error-handling coverage

**Status: Confirmed broken (two gaps), fixed.**

- (a) Narration: every error is spoken (`narrate(failure(message))`,
  `pageRetrying`, `pdfFailed`, `fillFailed`, `noSuchField`, `fieldNotFound`),
  EN and VI templates. **But** the `message` inside `failure(...)` was a
  hardcoded English literal in 8 places (`"Couldn't reach the AI
  service."`, `'The page did not load.'`, `PdfParseException.message`, …), so
  a Vietnamese user heard a Vietnamese sentence wrapping an English one. The
  submit failure spoke a raw `StateError.toString()`. Fixed: messages come
  from the narration lookup.
- (b) Retry by voice: **none existed.** `RetryRequested` had no caller in
  `lib/` (only the FSM and its tests). Automatic retries exist (page load,
  intent parse, field fill — each retried once through the FSM), but after
  the run ended in `ErrorState` the only recovery was pressing the button,
  which restarted from scratch. Fixed: after an error the app says how to
  retry and listens once; "retry"/"thử lại" resumes (at the final review for
  a failed submit, otherwise a fresh run, at most twice per run).

## Mic UX — design chosen before implementing

Problem: `VoiceTriggerButton` shows the same static mic in every state; the
mic is also live during the in-flow confirmations (`listenConfident` in the
per-field loop and final review) while the FSM state is `FillingForm`/
`FinalReview` — so **FSM state alone cannot tell whether the mic is open**,
and a state-driven icon would be wrong exactly when the user is speaking a
field value.

Approach (smallest change, no restructuring of the FSM, `SpeechService` or
the gate's contract): the **`VoiceCommandGate`** is the only place that calls
`speech.listen()`. It gets one narrow signal — an `onListening(bool)`
callback plus start/stop cue hooks — fired immediately around that call.
`ApplicationFlowController` (which owns the gate) republishes it as
`isListening` (it is already a `ChangeNotifier`). The button and the cues
therefore both hang off the same call site and cannot drift.

- Visual: three states with different **icon *and* colour** (WCAG 1.4.1) —
  idle `mic`, listening `hearing`/red, disabled `mic_off`/grey.
- Semantics label changes per state (`narration_lookup.dart`, EN/VI):
  "Start voice command" / "Listening…" / (disabled keeps the base label; the
  `enabled: false` flag conveys it).
- Audio: short spoken cue through the existing `TtsService` (no new plugin;
  Android's `SystemSoundType` offers only one usable sound, so it cannot give
  two distinct cues) — a start cue before `listen()` and, when speech was
  captured, a distinct stop cue. On silence/timeout the existing spoken
  re-prompt is the stop cue.

## 3. Summary — what can and cannot be assumed for a real Android device

**Safe to assume** (verified by static reading and unit/widget tests with
fakes — the logic, not the hardware):
- The OpenAI layer tolerates fenced/prose-wrapped/odd-cased replies, converts
  every failure to `OpenAiException`, retries 429/5xx/timeouts sensibly, and
  every call site degrades to non-AI behaviour.
- The flow's sequencing: gated submit, CAPTCHA pause-until-"continue" (audio or
  hand-off), announce-before-chooser and verify-after, per-field loop with the
  unrelated inputs filtered out, edit loop, voice retry (final review resume /
  fresh run, capped), localized error text.
- The mic button state and the audio cues come from one signal and are
  ordered (mic on → cue → listen → mic off → stop cue); labels/icons differ per
  state in EN and VI.
- Non-Android platforms get an explicit message instead of platform errors.
- 196 tests pass; `flutter analyze` is clean.

**Still needs a device** (not verified, not guessed):
- Real STT (Android often reports no confidence — mapped to 1.0; `vi_VN`
  recognition quality) and real TTS (Vietnamese voice pack; cue audibility and
  whether a spoken cue disturbs recognition).
- `sqflite` + `flutter_secure_storage` persistence and the Settings flow.
- The WebView bridge on a real WebView (`addWebMessageListener` support),
  page-load timeouts, the settle-wait against VietnamWorks, real DOM heuristics.
- The file chooser actually opening from a scripted `click()` (see the risk
  above), `AppLifecycleListener` timing, and the file name read-back.
- CAPTCHA detection and the audio-button selector on the real site.
- TalkBack navigation order and Accessibility Scanner (milestone 43).
- Feature 2 (`focus()` → TalkBack announcement, spike A1b).

**Still needs a live API key:** whether the real models obey the five prompts
(especially the < 0.7 confidence rule for ambiguous fields), intent accuracy
on real EN/VI utterances, vision transcription quality, cost/latency.

**Known gaps, not fixed** (need a device or a design decision): no navigation
from the listing page to the application form and no search step (1.8 #4);
the PDF must be picked by hand on a real run; the flow uses the single
`TARGET_URL` page.
